### 统一文件列表功能

三个 FileSection 实例统一支持：
- 单文件上传 / 下载
- 单文件新建 / 删除
- 文件夹新建 / 删除

| FileSection | 位置 | 生命周期 | baseUrl |
|-------------|------|---------|---------|
| 项目文件 | 左侧栏上半区 | 仅 L2 时渲染 | `/api/projects/{id}/files` |
| Library | 左侧栏下半区 | **始终渲染** | `/api/library/files` |
| Deliverables | 右侧面板 | activeProjectId 存在时渲染 | `/api/projects/{id}/files` |

左侧 L2 额外支持：
- Notebook 新建 / 删除（"+ New Notebook" 按钮）

左侧 L1 额外支持：
- 项目新建 / 删除

拖拽到 prompt：
- 所有 FileSection 的**普通文件**可拖拽到 prompt 输入框
- **Notebook (.notebook.json)** 不可拖拽（左侧项目文件区 `noDragFilter` 控制）

## 二、实施 Phase

### Phase 0: 后端 — 项目文件 CRUD 路由

> **[PROPOSED]** 文件: `packages/server/src/routes/projects.ts`

FileSection 组件需要标准 REST 端点，但项目路由只有 GET 列表，缺少 6 个 CRUD 路由。需新增：

| 路由 | 功能 |
|------|------|
| `POST /:projectId/files` | 上传文件（multer multipart） |
| `POST /:projectId/files/new-file?path=&name=` | 新建空文件 |
| `POST /:projectId/files/mkdir?path=&name=` | 新建文件夹 |
| `DELETE /:projectId/files?path=` | 删除文件/文件夹 |
| `GET /:projectId/files/download?path=` | 下载单个文件 |
| `GET /:projectId/files/zip` | 下载全部为 tar.gz |

复用 `validateWorkspacePath` + `listWorkspaceFiles` 工具函数，模式参照 `library.ts`。同时重构现有 GET 列表路由使用 `listWorkspaceFiles()`。

**修订 (C1)**: 更新 dotfile 过滤器：`.working/` 和 `.deliverables/` 目录需可见（现有过滤器仅放行 `.notebook.json` 和 `.index.json`）。dotfile 白名单用**精确匹配**（非前缀），避免意外暴露 `.git/`、`.env`。
**修订 (S1)**: 重构现有 GET 端点使用 `validateWorkspacePath()` 替代内联 `path.resolve()` 检查（防 symlink 穿越）。

**⚠ 回归防护 (RG-0)**: 重构 GET 列表改用 `listWorkspaceFiles()` 时，必须保持**响应 schema 不变**（`{ files: FileEntry[] }`，含 `name`/`type`/`size`/`mtime` 字段）。否则 ProjectSidebar 现有 FileBrowser 的解析逻辑立即崩溃。验证方法：重构前后对同一目录 curl 对比响应 JSON。

### Phase 2: 中心区域 — FileViewer 移入 notebook-area

> **[PROPOSED]** 文件: `packages/web/src/App.tsx`

将 `<FileViewer />` 移入 `.notebook-area` 内部。**Notebook 使用 `display:none` 保活**，而非条件卸载：

```tsx
<div className="notebook-area">
  {openFile && <FileViewer />}
  {gitTabOpen && activeProjectId ? (
    <GitHistoryPanel projectId={activeProjectId} />
  ) : notebookLoading ? (
    <NotebookLoadingScreen />
  ) : creatingNotebook ? (
    <NotebookCreationPanel />
  ) : hasNotebook ? (
    <div style={{ display: openFile ? 'none' : undefined }}>
      <Notebook />
    </div>
  ) : (
    <WelcomeScreen />
  )}
</div>
```

`.app-body` 添加条件 class `app-body--fv-maximized`（openFile && fileViewerMaximized 时生效）。

**修订 (C3)**: `setActiveNotebookTab` 时清除 `openFile`，避免 FileViewer 持有旧 sessionId。
**修订 (R1)**: FileViewer 打开/关闭时处理 notebook scroll 保存与恢复。

**⚠ 回归防护 (RG-2a) — display:none 保活**: 使用 `display:none` 而非条件卸载隐藏 Notebook，原因：
- 条件卸载会丢失 Cell 焦点、textarea 选区、uploadStatus timer、streaming 连接
- 滚动恢复依赖 `useEffect([notebookId])` — notebookId 未变则不触发 → 条件卸载后重新挂载会滚回顶部
- `nb:appendPrompt` CustomEvent 的 listener 在 NotebookInputBar 上 — Notebook 卸载后 listener 消失 → 批注"发送到 prompt"事件丢失

**⚠ 回归防护 (RG-2b) — 拖拽到 prompt**: FileViewer 打开时 Notebook 的 textarea 被 `display:none` 隐藏 → 仍然是合法 DOM 节点但不可见。需验证 `onDrop` 事件在 `display:none` 元素上是否仍可触发。若不可触发，FileViewer 打开时应禁用文件拖拽或显示提示。

**⚠ 回归防护 (RG-2c) — useFileStream 清理**: FileViewer 关闭时 `ws.removeEventListener` 执行，但服务端可能仍在发送 `file-open-chunk`。应在 cleanup 中发送 `file-close` 消息通知服务端停止推送。

## 三、回归防护体系

### 3.1 累积验证协议（每 Phase 完成后执行）

**核心原则：自动化层全量累积，手动层按依赖图定向回归。**

```
┌─────────────┐     ┌──────────────────────────────────┐     ┌─────────────┐
│  Phase N    │────>│  验证协议 (3 层)                  │────>│  Phase N+1  │
│  代码变更    │     │  全部通过才放行                    │     │             │
└─────────────┘     └──────────────────────────────────┘     └─────────────┘
```

#### 第一层：自动化全量累积（零成本，每步必跑）

| # | 检查项 | 命令 | 阻塞条件 |
|---|--------|-----|---------|
| 1 | **类型安全** | `cd packages/web && npx tsc --noEmit` | 任何 TS 错误 → 不进入下一 Phase |
| 2 | **全量测试套件** | `npm test`（跑 Phase 0~N 所有自动化测试） | 任何测试失败 → 不进入下一 Phase |
| 3 | **残留引用清扫** | `grep -r '被删除的标识符' packages/` | 有残留 → 清理后重跑 1-2 |

测试套件随 Phase 推进**只增不减**，后续 Phase 的 `npm test` 自动覆盖所有前序 Phase 的测试：

```
Phase 0 完成: npm test 跑 T0 (5 个后端路由测试)
Phase 1 完成: npm test 跑 T0 + T1 (+ 3 个 store 测试)
Phase 2 完成: npm test 跑 T0 + T1 + T2 (+ 若干补写测试)
...
Phase 8 完成: npm test 跑 T0..T8 (全量安全网)
```

#### 第二层：当前 Phase 新功能验证（手动）

按 Phase 目标行为手动测试本步新增功能。不满足 → 不进入下一 Phase。

#### 第三层：依赖图定向回归（手动，非盲目全验）

**只验"本 Phase 修改的 state/props/CSS 被哪些组件消费"**，不盲目从头验所有旧功能：

```
Phase N 完成时：
├─ 自动化层: tsc + npm test（全量累积，零成本）        ✅ 已覆盖纯逻辑回归
├─ 当前 Phase: 手动验新功能 checklist                 ✅ 确认新行为正确
└─ 回归层: 手动验"本 Phase 的变更影响了哪些消费方"      ✅ 定向检查，不线性膨胀
```

**各 Phase 回归验证范围：**

| Phase | 修改了什么 | 定向回归验证（消费方） |
|-------|-----------|---------------------|
| Phase 0 | GET /files 响应格式 | ProjectSidebar FileBrowser 文件列表是否正常显示 |
| Phase 1 | store 删 `filesPanelOpen`，加 `leftSidebarSplitRatio` | 不验（自动化测试覆盖） |
| Phase 2 | `<FileViewer>` 位置 + `display:none` Notebook | Notebook 滚动恢复、cell streaming、拖拽到 prompt |
| Phase 3 | CSS 删除 `.files-panel` 等 | FileSection 样式（`.fp-entry` 等）未受影响 |
| Phase 4 | FileBrowser → FileSection 替换 | `.notebook.json` 打开流程、拖拽到 prompt |
| Phase 5 | 文件重命名 | 不验（tsc + grep 已覆盖） |
| Phase 6 | NotebookTabs 新增文件标签 | tab 切换 → Notebook 恢复、无闪烁 |
| Phase 7 | 四层原子更新 `'deliverables'` | FileViewer 打开 deliverables 文件、拖拽到 prompt |
| Phase 8 | Toolbar 按钮移除 | 不验（tsc 已覆盖） |

**为什么不每步手动全验**：自动化测试已覆盖纯逻辑回归，剩余手动验证应聚焦在"自动化测试覆盖不到的 DOM/视觉/交互"层面，且只验被当前变更影响到的消费方。否则手动验证成本随 Phase 推进线性膨胀，违背 TDD 快速反馈的精神。

### 3.2 TDD 适配方案

#### 核心矛盾

本项目工作流要求所有改动走 Red/Green TDD，但本次重构 ~60% 的变更是 DOM/CSS/组件生命周期，传统单元测试覆盖不了。

#### TDD 的本质（不是"写测试"）

TDD 的价值是两件事：
1. **先定义期望行为，再写实现**（思维纪律）
2. **快速反馈循环捕获回归**（安全网）

单元测试只是这两件事的**一种实现方式**。当单元测试覆盖不了时，需要用替代机制保持同样的纪律和安全网。

#### 三种 TDD 变体

**变体 A：经典 Red/Green（Phase 0, 1, 7 — 纯逻辑）**

完全适用标准 TDD：

```
Phase 0 示例：
  Red:   test('GET /files hides .git directory')           → FAIL
  Green: 更新 dotfile 白名单，精确匹配 .working/.deliverables → PASS

Phase 7 示例：
  Red:   test('source=deliverables resolves to .deliverables dir') → FAIL
  Green: ws-handler 加 deliverables 分支                            → PASS
  Red:   test('unknown source throws, not silent fallback')         → FAIL
  Green: default 分支加 throw                                       → PASS
```

这些测试在后续 Phase 中**持续运行**，构成永久安全网。

| Phase | 可测试内容 | Red 测试示例 |
|-------|-----------|-------------|
| Phase 0 | 后端 CRUD 路由 | `test('POST /files uploads file')`, `test('GET /files returns .working contents')`, `test('GET /files hides .git directory')` |
| Phase 1 | Store 状态变更 | `test('setOpenFile with deliverables source')`, `test('leftSidebarSplitRatio clamps 0.2~0.8')` |
| Phase 7 | ws-handler basedir | `test('source=deliverables resolves to .deliverables dir')`, `test('unknown source throws')` |

**变体 B：Spec-First Checkpoint（Phase 2, 3, 4, 6 — DOM/CSS/生命周期）**

"写测试"变成"写检查清单"，纪律结构不变：

```
                    经典 TDD              Spec-First Checkpoint
                    ─────────             ─────────────────────
1. 定义期望行为      写 test()             写检查清单（变更前完成）
2. 确认当前失败      运行测试 → Red        手动操作 → 观察到旧 bug
3. 实施变更          写最少代码            改代码
4. 验证通过          运行测试 → Green      走检查清单 → 全部 ☑
5. 发现意外回归      测试 catch            检查清单 catch → 转入变体 C
```

Phase 2 检查清单示例（**变更前写好** = 等价于"先写 Red test"）：

```
□ 打开文件 → FileViewer 占据 notebook-area 完整区域（不在底部）
□ 关闭文件 → Notebook 恢复显示，滚动位置正确
□ 打开文件时 → Notebook 的 cell streaming 不中断（display:none 不杀进程）
□ 打开文件时 → 从 Library 拖拽文件到 prompt → 验证 drop 行为
□ 最大化 → 左右侧栏隐藏，中心区铺满
□ 取消最大化 → 侧栏恢复
□ 切换 notebook tab → FileViewer 关闭
□ tsc --noEmit → 零错误
```

| Phase | 验证内容 | 为什么不能经典 TDD |
|-------|---------|-------------------|
| Phase 2 | FileViewer ↔ Notebook display:none 切换 | DOM 可见性 + scroll 位置 = 需要浏览器环境 |
| Phase 3 | CSS 删除后样式不丢失 | 视觉回归需要截图对比或人工检查 |
| Phase 4 | FileBrowser → FileSection 替换后 notebook 可打开 | 涉及多组件交互链 + WS 通信 |
| Phase 6 | Tab 切换无闪烁 | 时序问题，需运行时观察 |

**变体 C：补写固定测试（任何 Phase 发现意外回归时）**

关键桥梁 — **把变体 B 中发现的问题拉回变体 A 的轨道**：

```
Phase 4 执行中，检查清单发现意外回归：
  .notebook.json 点击不再打开 notebook

不是直接修复，而是：

1. 先写测试（拉回 Red）：
   test('onFileClick with .notebook.json calls openNotebookByPath', () => {
     const openMock = vi.fn();
     handleFileClick('.', 'test.notebook.json', { openNotebookByPath: openMock });
     expect(openMock).toHaveBeenCalledWith('project-1', '.working/test.notebook.json');
   });

2. 确认失败 → Red ✓
3. 修复 onFileClick 回调 → Green ✓
4. 这个测试永久留在测试套件中，后续 Phase 不会再引入同类回归
```

#### 三种变体的协作关系

```
                        ┌─────────────────────────────┐
                        │  TDD 纪律（不变）            │
                        │  = 先定义期望 → 再实现       │
                        └──────────┬──────────────────┘
                                   │
                    ┌──────────────┼──────────────────┐
                    │              │                   │
              变体 A: 自动化     变体 B: 手动         变体 C: 补写
              (纯逻辑)          (DOM/CSS)            (意外回归)
                    │              │                   │
              test() → Red    检查清单 → ☐          发现 bug →
              code  → Green   code → ☑             先写 test → Red
              持续运行 ✓      人工验证 ✓            修复 → Green
                    │              │                持续运行 ✓
                    │              │                   │
                    └──────────────┼───────────────────┘
                                   │
                                   ▼
                    安全网随 Phase 推进不断增厚：
                    Phase 0 完成: 5 个自动化测试
                    Phase 2 完成: 5 + 检查清单归档
                    Phase 4 完成: 5 + 2 个补写测试 + 检查清单
                    Phase 7 完成: 5 + 2 + 3 个新自动化测试
                    全部完成:     10+ 自动化测试 + 检查清单归档为验收文档
```

#### 为什么不全部用 Playwright E2E 覆盖

| 因素 | 单元测试 | Playwright E2E |
|------|---------|---------------|
| 反馈速度 | < 100ms | 5-15s |
| 依赖环境 | 无 | 完整前后端启动 |
| CSS 视觉回归 | 不支持 | 需截图基线维护 |
| 与 TDD 快速迭代精神 | 契合 | **退化到分钟级** |

策略：变体 B（手动检查清单）保持快速迭代，变体 C（补写测试）逐步把高价值检查项自动化。项目 CLAUDE.md 也约定"只在用户明确要求时才启动 Playwright"，与此策略一致。

#### 实施纪律汇总

```
对于可 TDD 的部分（Phase 0/1/7）→ 变体 A：
  1. Red   — 先写失败测试，定义期望行为
  2. Green — 写最少代码让测试通过
  3. 检查门 — tsc + 冒烟
  4. 进入下一 Phase

对于不可 TDD 的部分（Phase 2/3/4/5/6）→ 变体 B + C：
  1. 写检查清单（变更前完成）
  2. 实施变更
  3. 走检查清单 + 检查门（tsc + 冒烟）
  4. 发现问题 → 变体 C：补写测试固定 bug → 修复 → 重跑检查
  5. 进入下一 Phase
```
