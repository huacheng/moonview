# Design Proposal: `read` and `security` Sub-commands

This document outlines the detailed architectural design, execution logic, and integration points for the `/moonview:read` and `/moonview:security` sub-commands within the `task-ai` framework.

---

## 1. `/moonview:read` — The Knowledge Synthesizer

**Objective**: Safely ingest external documents (local files provided by the user), extract novel domain knowledge, deduplicate against the existing library, and synthesize it into validated `.references/` files.

### 1.1 Command Interface
```bash
/moonview:read <file_path> [--depth shallow|deep]
```
*   `file_path`: Absolute or relative path to the local document (e.g., PDF, Markdown, text).
*   `--depth shallow`: Fast ingestion. Extracts core concepts, summarizes, formats as a reference, and applies detox.
*   `--depth deep`: Comprehensive ingestion. Performs `shallow` steps, PLUS triggers Web research to cross-validate claims, fetch the latest API updates, and ensure the knowledge is authoritative before saving.

### 1.2 The Detox Policy (Answering the `shallow` mode question)
**YES. `shallow` mode MUST go through the exact same detox logic as `research`.**
*   **Rationale**: The source of the document is external (provided by the user). It may have been downloaded from the internet or generated by an untrusted source. It could contain latent prompt injections, malicious markdown formatting, or encoded payloads (Category 1-10 injection risks).
*   **Enforcement**: Before any content is written to `$NB_WORKSPACES_LIBRARY/.memory/.references/`, the text MUST pass through the 10-category injection protection pipeline defined in `library/references/injection-rules.md`. If a high risk is detected, the ingestion is either sanitized or wrapped in an isolation block.

### 1.3 Execution Steps (SKILL.md draft)
1.  **Ingestion & Parsing**: Read the file. If binary (PDF/Docx), delegate to `doc-parse` plugin.
2.  **Entity Extraction**: Identify the primary `topic`, `type` (domain), and key concepts.
3.  **Library Deduplication (Layer 1)**: Run `library search` using extracted concepts. Identify what the library already knows.
4.  **Delta Extraction**: Isolate the *novel* information in the document (the "delta"). If the document is 100% redundant, abort and notify the user to save context window.
5.  **Depth Processing**:
    *   *If `shallow`*: Synthesize the delta into a markdown structure.
    *   *If `deep`*: Formulate search queries based on the delta. Execute Web searches to cross-reference (e.g., "Is this API deprecated?", "What are the security gotchas for this pattern?"). Merge web findings with the document delta.
6.  **Sanitization (Detox)**: Apply the 10-category injection rules. Compute `injection_risk` and hashes.
7.  **Library Write Protocol**: Acquire `.references/.lock`, write to `.memory/.references/<topic>.md`, update `.changelog` (action: `read`, source: `file_path`), update `.index.md`, release lock.
8.  **Index Rebuild**: Trigger `library maintain --rebuild-index`.

## 2. `/moonview:security` — The Runtime Guardian

**Objective**: Act as the framework's immune system, proactively auditing plans and intercepting high-risk shell commands before execution. It prevents latent malicious instructions (which might have survived ingestion) from causing irreversible damage.

### 2.1 Command Interface
```bash
/moonview:security <notebook> <action> [payload]
```
*   `action: audit-plan`: Scans `.plan.md` and `.target.md` for semantic deviation and dangerous structural intents.
*   `action: verify-cmd`: Evaluates a specific shell command string for destructive potential.
*   `payload`: The specific command string when using `verify-cmd`.

### 2.2 Integration with the `task-ai` Lifecycle
`security` is not just a standalone tool; it acts as a mandatory **Pre-hook** for existing sub-commands.

#### Integration Point 1: The `check` Sub-command (Planning Phase)
*   **When**: During `check --checkpoint post-plan`.
*   **Action**: `check` must invoke `/moonview:security <notebook> audit-plan`.
*   **Logic**: 
    1. Scans `.plan.md` against a manifest of forbidden operations (e.g., altering Git history of the main repo, deleting directories outside the workspace).
    2. **Semantic Alignment**: Verifies that the proposed implementation steps logically align with the `.target.md` requirements. If the plan introduces unrequested networking or obfuscated execution, it flags it.
*   **Outcome**: If `security` returns `BLOCKED` or `HIGH_RISK`, the `check` sub-command immediately renders a `REPLAN` verdict with the security report attached.

#### Integration Point 2: The `exec` Sub-command (Execution Phase)
*   **When**: During step-by-step execution in `exec.sh`, *before* issuing any shell command that modifies state (file deletion, system config, package installation, network requests).
*   **Action**: The AI Agent executing the plan MUST invoke `/moonview:security <notebook> verify-cmd "<command>"`.
*   **Logic**:
    1. **Command Syntax Parsing**: Checks for dangerous flags (Category 10 VFP injection: `--conftest`, `--eval`), two-stage payloads (`curl | bash`), and destructive targets (`rm -rf /`, `chmod -R 777`).
    2. **Scope Confinement**: Ensures the command only operates within the `$NB_WORKSPACES_ROOT/<project>/<notebook>/` directory or the isolated `.worktrees/` path. Any attempt to traverse up (`../../`) or modify global system paths is intercepted.
*   **Outcome**: 
    *   If `PASS`: The command is executed.
    *   If `REJECT`: The execution is halted. `exec` logs the failure, signals `(mid-exec)`, and transitions the state to `NEEDS_FIX`.

### 2.3 The "Lineage Tracing" Mechanism (Self-Healing)
If `security verify-cmd` intercepts a malicious command during `exec`, the system must prevent future tasks from falling into the same trap.
1.  **Trace**: `security` instructs the Agent to search `.plan.md` and `.notes/` to find which `.references/` or `.experiences/` file suggested the malicious command.
2.  **Isolate**: Once identified, `security` updates the source file's frontmatter:
    *   Increments `failure_count`.
    *   Upgrades `injection_risk` to `high`.
    *   Sets `status` to `invalidated`.
3.  **Audit Trail**: The incident is recorded in `.analysis/<date>-security-breach.md`.

### 2.4 Summary of `security` Interactions
| Sub-command | Interaction with `security` | Consequence of Failure |
| :--- | :--- | :--- |
| `check` | Calls `audit-plan` to review `.plan.md`. | Verdict `REPLAN`, phase `needs-plan`. |
| `exec` | Calls `verify-cmd` before risky shell actions. | Aborts step, signals `(mid-exec)`, `NEEDS_FIX`. |
| `read` / `research` | Indirect: `security` defines the 10-category rules they apply. | Content sanitized or rejected at ingestion. |
